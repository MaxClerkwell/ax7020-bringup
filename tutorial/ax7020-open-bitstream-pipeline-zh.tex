\section{本教程要搭建什么}

ALINX AX7020 是一块 Zynq-7000 开发板：两个 Cortex-A9 核心与一块 7 系列 FPGA
逻辑阵列 (fabric) 集成在同一颗芯片上，处理器侧配有 1\,GiB DDR3、32\,MiB QSPI
闪存和千兆以太网。厂商推荐的路线是 Vivado、Xilinx FSBL、PetaLinux 和一张 SD 卡。
本教程走另一条路：把上述每一个环节都换成源码可读的组件。

\subsection{你需要准备什么}

\begin{itemize}
  \item 一块 ALINX AX7020，带 12\,V 电源和一根以太网线。
  \item 一个 JTAG 适配器。一块 FTDI FT232H 开发板就够了；这块板子不需要复位线，
        也不需要缓冲使能线。
  \item 一台 Linux 工作站（本文使用 Debian 13），带第二个以太网口或 USB 网卡用于
        搭建私有实验网络，约 100\,GB 空闲磁盘空间给 Yocto，以及几个小时的构建时间。
  \item 公司网络或实验室网络中一台能跑一个 nginx 容器的机器。路由器或 NAS 最合适。
  \item 不需要 SD 卡、USB-UART 线、Vivado 或 PetaLinux。
\end{itemize}

\section{主机环境}

\subsection{工具链与工具}

\begin{shell}
sudo apt install gcc-arm-none-eabi openocd python3 make git
sudo apt install gawk wget diffstat unzip texinfo gcc build-essential \
    chrpath socat cpio python3-pip python3-pexpect xz-utils debianutils \
    iputils-ping python3-git python3-jinja2 python3-subunit zstd lz4 file \
    locales libacl1
\end{shell}

第二行是 Yocto 在 Debian 上的主机依赖列表。注意这里是 \cmd{lz4} 而不是旧的
\cmd{liblz4-tool}；Yocto 仍然按旧名字 \cmd{lz4c} 查找该二进制文件，
\rfile{yocto/hostbin/lz4c} 是一个符号链接，无需 root 权限即可解决这个问题。

\subsection{JTAG 适配器}

\rfile{openocd/ft232h.cfg} 描述了一块裸 FT232H。在 FTDI 芯片上，MPSSE 引脚分配
是硅片固定的（ADBUS0 = TCK，1 = TDI，2 = TDO，3 = TMS），所以只需声明空闲电平和方向：

\begin{code}
adapter driver ftdi
ftdi vid_pid 0x0403 0x6014
ftdi layout_init 0x0008 0x000b
adapter speed 1000
transport select jtag
\end{code}

\begin{shell}
openocd -f openocd/ft232h.cfg -f target/zynq_7000.cfg
\end{shell}

\begin{checkpoint}
扫描链上显示两个 TAP 和两个核心：
\begin{code}
JTAG tap: zynq_pl.bs tap/device found: 0x23727093 (Xilinx, part 0x3727)
JTAG tap: zynq.cpu   tap/device found: 0x4ba00477 (ARM Ltd)
zynq.cpu0: hardware has 6 breakpoints, 4 watchpoints
zynq.cpu1: hardware has 6 breakpoints, 4 watchpoints
\end{code}
\end{checkpoint}

\subsection{实验网络}

板级启动阶段，开发板挂在工作站后面的一个私有网络上。用 NetworkManager 的
\emph{共享} (shared) 连接提供 DHCP，同时把开发板隔离在家庭网络之外：

\begin{shell}
nmcli connection add type ethernet ifname <iface> con-name zynq-lab \
    ipv4.method shared ipv4.addresses 192.168.77.1/24 ipv6.method disabled
nmcli connection up zynq-lab
\end{shell}

开发板拿到租约后，用 \cmd{ip neigh show dev <iface>} 查找它的地址。

\subsection{控制台与 TFTP}

这套方案里没有串口线。U-Boot 的控制台是它的\emph{网络控制台} (netconsole)，走 UDP
6666 端口，\rfile{tools/ncsh.py} 是与之配套的 shell。\rfile{tools/tftpd.py}
是一个非特权 TFTP 服务器，因此不需要任何系统服务：

\begin{shell}
tools/tftpd.py tftp 6969 &                  # serves the tftp/ directory
tools/ncsh.py <board-ip>                    # interactive
tools/ncsh.py <board-ip> "bdinfo" "sf probe 0 30000000 0"   # one-shot
\end{shell}

在开发板上，\cmd{setenv tftpdstp 6969} 让 \cmd{tftpboot} 指向这个端口。

\section{阶段 1：把主线 U-Boot 写入 QSPI 闪存}

主线 U-Boot 不支持 AX7020。四个文件让它认识这块板子；它们镜像在
\file{uboot/} 目录下，需要放进 \cmd{v2026.10-rc2} 或更新版本的 U-Boot 源码树中。

\subsection{四个文件}

\begin{filelist}
  \item[\rfile{uboot/zynq-ax7020.dts}] \file{arch/arm/dts/}。开发板描述，每个值都由厂商的硬件交接文件 (hardware handoff) 和原理图推导而来。
  \item[\rfile{uboot/alinx_ax7020_defconfig}] \file{configs/}。由 \cmd{xilinx\_zynq\_virt\_defconfig} 派生：启用 netconsole、传统网络栈、TFTP put、md5sum；关闭 SPL 的 FIT 加载和重定位的 SPL 栈。
  \item[\rfile{uboot/ps7_init_gpl.c}, \file{.h}] \file{board/xilinx/zynq/zynq-ax7020/}。Vivado 生成的 PS 初始化代码（PLL、MIO、DDR 时序），从厂商的 XSA 归档中提取，XSA 其实就是一个普通 zip。为适配 GCC 15，五处声明加上了 \cmd{(void)}。
\end{filelist}

再做两处修改即可完成：把 \cmd{zynq-ax7020.dtb} 加入
\file{arch/arm/dts/Makefile}；在 \file{include/configs/zynq-common.h} 的默认环境中
设置 \cmd{ncip} = \cmd{255.255.255.255} 以及
\cmd{stdin}/\cmd{stdout}/\cmd{stderr} = \cmd{serial,nc}，这样在环境变量可写之前，
netconsole 就已经就位。

\begin{mustknow}
这块板子上有两条设备树 (device tree) 规则是强制的。\cmd{bootph-all} 必须同时出现在
闪存节点\emph{和} QSPI 控制器节点上，否则 SPL 找不到片选。而且 \cmd{spi-rx-bus-width}
必须是 \cmd{<1>}：在 SPL 中，四线读 (quad read) 返回的数据会偏移三个字节，
而完整的 U-Boot 不会暴露这个故障。
\end{mustknow}

\subsection{编译}

启动命令直接编译进二进制，而不是存在环境变量里，因为 JTAG 启动模式下
\cmd{saveenv} 不起作用，而且过长的 \cmd{setenv} 命令行会在 netconsole 上断裂。
它从 FIT 分区读取 24\,MiB：

\begin{code}
CONFIG_BOOTCOMMAND="sf probe 0 30000000 0; sf read 0x2000000 0x340000 0x1800000; bootm 0x2000000"
\end{code}

\begin{shell}
cd u-boot
make alinx_ax7020_defconfig
scripts/config --disable TOOLS_MKEFICAPSULE      # host tool needs gnutls
make olddefconfig
make -j$(nproc) CROSS_COMPILE=arm-none-eabi-
cp spl/boot.bin u-boot.img ../tftp/
\end{shell}

\begin{checkpoint}
生成了 \file{spl/boot.bin}（约 107\,kB，带 Xilinx 启动头的 SPL）和
\file{u-boot.img}（约 1.1\,MB，传统 uImage 格式）。
\end{checkpoint}

\subsection{闪存布局}

\begin{center}\small
\begin{tabular}{@{}llll@{}}
\toprule
偏移 & 内容 & 分区大小 & mtd \\
\midrule
\cmd{0x000000} & \file{boot.bin} & 1\,MiB & 0 \\
\cmd{0x100000} & \file{u-boot.img} & 2\,MiB & 1 \\
\cmd{0x300000} & 环境变量 + 冗余副本 & 256\,KiB & 2 \\
\cmd{0x340000} & FIT：内核 + DTB + initramfs & 28.75\,MiB & 3 \\
\bottomrule
\end{tabular}
\end{center}

Linux 设备树中有同一张映射表，所以运行中的 Linux 会把这些分区看作
\file{/dev/mtd0..3}。

\subsection{通过 JTAG 完成板级启动}

开发板冷态，J13 拨到 JTAG，上电。\rfile{openocd/load-uboot.cfg} 把 SPL 加载到
片上内存，等待 \cmd{ps7\_init} 把 DDR 初始化完成，写入并回读一个 DDR 测试字，
把完整 U-Boot 加载到 \cmd{0x4000000}，校验后跳转：

\begin{shell}
openocd -f openocd/ft232h.cfg -f target/zynq_7000.cfg -f openocd/load-uboot.cfg
\end{shell}

\begin{mustknow}
只在 \emph{SPL} 处于停机 (halt) 状态、缓存关闭时加载完整 U-Boot。若在一个先前的
完整 U-Boot 停机时向 DDR 加载，其已启用的 D-cache 会以 32 字节为单位破坏镜像。
另外，任何一次 QSPI 模式启动之后，再次通过 JTAG 加载前必须在 JTAG 模式下重新上电：
\cmd{ps7\_init} 不是幂等的。
\end{mustknow}

\begin{checkpoint}
通过 netconsole，\cmd{bdinfo} 报告 1\,GiB DRAM，
\cmd{sf probe 0 30000000 0} 检测到 \cmd{w25q256}，容量 32\,MiB。
\end{checkpoint}

\subsection{烧写}

只能从一个"在 JTAG 模式下刚重新上电、并通过 JTAG 加载"的 U-Boot 执行。
大小是文件大小的十六进制表示
（\cmd{printf "\%x\textbackslash n" \$(stat -c \%s tftp/boot.bin)}）：

\begin{shell}
tools/ncsh.py <ip> "setenv tftpdstp 6969" "sf probe 0 30000000 0" \
  "tftpboot 0x10000000 boot.bin" "tftpboot 0x11000000 u-boot.img" \
  "md5sum 0x10000000 <size_boot_bin>" "md5sum 0x11000000 <size_u_boot_img>"
tools/ncsh.py <ip> "sf erase 0 0x300000" \
  "sf write 0x10000000 0 <size_boot_bin>" \
  "sf write 0x11000000 0x100000 <size_u_boot_img>"
tools/ncsh.py <ip> "sf read 0x12000000 0 <size_boot_bin>" \
  "md5sum 0x12000000 <size_boot_bin>" \
  "sf read 0x13000000 0x100000 <size_u_boot_img>" \
  "md5sum 0x13000000 <size_u_boot_img>"
\end{shell}

\begin{checkpoint}
两个回读的 MD5 都与主机上 \cmd{md5sum} 计算的结果一致。在此之前，
任何东西都不算烧写成功。
\end{checkpoint}

\subsection{独立启动}

断电，J13 拨到 QSPI，拔掉 JTAG，上电。

\begin{checkpoint}
U-Boot 自行出现在 netconsole 上，且 \cmd{modeboot = qspiboot}。
JTAG 适配器可以收进抽屉了；从这里开始，一切都通过以太网完成。
\end{checkpoint}

\section{阶段 3：闪存中的 Yocto Linux}

\emph{阶段编号沿用系列文章的顺序，阶段 2 的镜像服务器实际上是在阶段 3 的 Linux
之后才搭建的。}

Linux 需要的一切打包成一个制品：一个包含内核、设备树和 initramfs 的 FIT 镜像，
写入 FIT 分区。根文件系统位于 RAM 中。这个镜像就是\emph{维护系统}：体积小，
很少变动，负责获取其余的一切。

\subsection{层 (layer)}

全程使用 \cmd{scarthgap}（Yocto 5.0 LTS），这是 meta-xilinx 支持的最新分支：

\begin{shell}
cd yocto
for r in "https://git.yoctoproject.org/poky poky" \
         "https://github.com/Xilinx/meta-xilinx meta-xilinx" \
         "https://git.yoctoproject.org/meta-arm meta-arm" \
         "https://github.com/openembedded/meta-openembedded meta-openembedded"; do
    set -- $r; git clone --depth 1 -b scarthgap "$1" "$2"
done
\end{shell}

\rfile{yocto/meta-ax7020} 是开发板层。其组成部分如下，路径相对于该层：

\begin{filelist}
  \item[\lfile{conf/machine/ax7020.conf}] 引用 meta-xilinx 的 \cmd{zynq-generic}，把 \cmd{KERNEL\_IMAGETYPE} 设为 \cmd{fitImage}，不声明任何 bootloader 提供者，并指定 \cmd{ax7020-initramfs} 作为放进 FIT 的 initramfs。
  \item[\lfile{recipes-kernel/linux/files/zynq-ax7020.dts}] Linux 设备树，包含闪存分区映射。
  \item[\lfile{recipes-kernel/linux/files/ax7020.cfg}] 内核配置片段：Zynq FPGA manager、FPGA region 与 overlay、netconsole、MTD 与 QSPI、kexec；关闭图形、声音、无线和 IPv6。
  \item[\lfile{recipes-core/images/ax7020-initramfs.bb}] 维护镜像：core-image-minimal 打包为 \cmd{cpio.gz}，外加 dropbear、curl、kexec-tools、更新器和操作员的 SSH 公钥。
  \item[\lfile{recipes-support/ax7020-ssh-key}] 把 \file{authorized_keys} 安装到 \cmd{\$\{ROOT\_HOME\}}。构建前，把你的公钥放到 \rfile{yocto/meta-ax7020/recipes-support/ax7020-ssh-key/files/authorized_keys}。
  \item[\rfile{yocto/setup-build.sh}] 从版本控制中重新生成 \file{build/conf}：machine 为 \cmd{ax7020}，\cmd{INIT\_MANAGER = "systemd"}，Yocto 不构建 bootloader。
\end{filelist}

\subsection{构建}

\begin{shell}
source yocto/setup-build.sh
setsid nohup bitbake virtual/kernel > build.log 2>&1 &     # detached: a killed
tail -f build.log                                          # client kills the build
\end{shell}

首次构建需要几个小时。FIT 输出在
\file{yocto/build/tmp/deploy/images/ax7020/} 下，文件名为
\file{fitImage-ax7020-initramfs-ax7020-ax7020}；把它复制到 \file{tftp/fitImage}。

\begin{checkpoint}
\cmd{dumpimage -l tftp/fitImage} 列出一个配置，包含内核、DTB
\cmd{zynq-ax7020.dtb} 和一个 ramdisk，每一项都带 SHA256 哈希。FIT 小于 24\,MiB。
\end{checkpoint}

\subsection{先从 RAM 启动}

从一个通过 JTAG 加载的 U-Boot 开始，在写入任何东西之前：

\begin{shell}
tools/ncsh.py <ip> "setenv tftpdstp 6969" "tftpboot 0x2000000 fitImage" "bootm 0x2000000"
\end{shell}

\begin{checkpoint}
Linux 启动，以主机名 \cmd{ax7020} 获取 DHCP 租约，并且
\textbf{22 端口有响应}，仅允许密钥登录。ping 不能作为判据；
一个网络栈正常的 U-Boot 同样会响应 ping。
\end{checkpoint}

\subsection{烧写 FIT}

\begin{shell}
tools/ncsh.py <ip> "setenv tftpdstp 6969" "tftpboot 0x2000000 fitImage" \
  "sf probe 0 30000000 0" "sf erase 0x340000 0x1CC0000" \
  "sf write 0x2000000 0x340000 <size_fit>" \
  "sf read 0x3000000 0x340000 <size_fit>" "md5sum 0x3000000 <size_fit>" \
  "md 0x3000000 4" "md 0x3800000 4"
\end{shell}

\begin{checkpoint}
回读的 MD5 一致，\emph{并且}回读数据中两个不同偏移处的字彼此不同。
一块地址线错位的闪存可能返回一份自洽却错误的镜像，单一校验和是查不出来的。
\end{checkpoint}

断电，J13 拨到 QSPI，上电。

\begin{checkpoint}
Linux 自行从闪存启动，可以通过 SSH 访问。此时开发板可以从实验网络
移到公司网络；它会以 \cmd{ax7020} 的名字向 DHCP 报到。
\end{checkpoint}

\section{阶段 2：镜像服务器与更新器}

维护系统从不改动闪存中的内容。每次启动时，它向一个 URL 请求清单 (manifest)，
下载内核、设备树和 initramfs，校验之后 \cmd{kexec} 进入结果。一个坏掉的镜像
只需要重新上电，而不必重新烧写，因为重新上电后维护系统就回来了。

\subsection{服务器}

在开发板能访问到的一台机器上跑一个 nginx 容器，只读，只绑定 LAN 地址，
提供一个目录：

\begin{shell}
docker run -d --name ax7020-image-server --restart unless-stopped \
  -p 10.42.0.1:8080:80 \
  -v /srv/ax7020-images:/usr/share/nginx/html:ro \
  -v /etc/ax7020-image-server/default.conf:/etc/nginx/conf.d/default.conf:ro \
  --read-only --tmpfs /var/cache/nginx --tmpfs /var/run --tmpfs /tmp nginx:alpine
\end{shell}

\file{default.conf} 中包含 \cmd{autoindex on;} 和 \cmd{disable\_symlinks off;}。
每次构建得到一个带时间戳的目录；\file{ax7020-latest} 是指向最新目录的符号链接。
开发板只知道一个 URL：

\begin{code}
http://10.42.0.1:8080/ax7020-latest/manifest
\end{code}

\subsection{发布}

\rfile{tools/publish-image.sh} 通过 scp 把 zImage、DTB 和 \cmd{cpio.gz} 从 Yocto
的 deploy 目录复制过去，写入带 SHA256 校验和的清单，然后重新指向符号链接：

\begin{shell}
tools/publish-image.sh AI-heimdall:/srv/ax7020-images                  # API image
tools/publish-image.sh -i ax7020-initramfs AI-heimdall:/srv/ax7020-images   # maintenance image
\end{shell}

\begin{code}
kernel zImage             542ef58f...
dtb    zynq-ax7020.dtb    1e3fa9c7...
initrd initramfs.cpio.gz  4e73ba34...
\end{code}

\begin{mustknow}
清单列出的是三个文件，而不是一个 FIT。32 位 ARM 上的 \cmd{kexec-tools} 没有 FIT
加载器，而它的 zImage 探测逻辑接受任何文件；给它一个 FIT，它会跳进设备树，
开发板悄无声息地死掉。更新器会自己检查偏移 \cmd{0x24} 处的 zImage 魔数
和 DTB 魔数，因为下游没有任何环节会检查。
\end{mustknow}

\subsection{更新器}

更新器位于 \rfile{yocto/meta-ax7020/recipes-support/ax7020-updater/files/}：
\file{ax7020-update} 是 shell 脚本，\file{ax7020-update.conf} 设置
\cmd{IMAGE\_URL}（留空表示\emph{留在维护系统}），
\file{ax7020-update.service} 每次启动运行它一次：

\begin{code}
[Unit]
After=network-online.target time-sync.target
Wants=network-online.target

[Service]
Type=oneshot
ExecStartPre=/bin/sleep 15
ExecStart=/usr/bin/ax7020-update
StandardOutput=journal+console
\end{code}

脚本获取清单，然后逐个下载文件，比对每个 SHA256，检查两个魔数，
执行 \cmd{kexec -l zImage --dtb --initrd --command-line}，随后 \cmd{kexec -e}。
\cmd{DRY\_RUN=1} 会在跳转前停下。任何一步失败，unit 就失败，开发板仍可通过
SSH 访问。

\begin{checkpoint}
把维护镜像本身发布出去，设置 \cmd{IMAGE\_URL}，重启：大约二十秒后，
同一个系统回来了，运行时间 (uptime) 只有几秒，而
\cmd{journalctl -u ax7020-update} 显示三个校验和均已通过。
\end{checkpoint}

\section{阶段 4：不用 Vivado 生成比特流}

\subsection{工具链}

Zynq-7020 是 7 系列器件，在 openXC7 流程的覆盖范围内。
除 Yosys 之外，一切都在 \file{build/} 下从源码构建：

\begin{center}\small
\begin{tabular}{@{}lll@{}}
\toprule
工具 & 来源 & 作用 \\
\midrule
Yosys 0.66 & Debian 软件包 & 综合，\cmd{synth\_xilinx} \\
nextpnr-xilinx & openXC7 分支 & 布局布线，可读取 XDC \\
prjxray & f4pga & \cmd{fasm2frames}、\cmd{xc7frames2bit} \\
prjxray-db & zynq7 & 比特流数据库，\cmd{xc7z020} 的 chipdb \\
\bottomrule
\end{tabular}
\end{center}

XC7Z020 的芯片数据库 (chipdb) 由 prjxray-db 生成一次；它有几百兆字节，
下面的一切都依赖它。

\subsection{设计}

\rfile{bitstream/blinky/blinky.v}：一个由 50\,MHz PL 振荡器驱动的 27 位计数器，
高位接四个 LED，还有一行不可省略的代码：

\begin{code}
module blinky (input wire sys_clk, output wire [3:0] led);
    reg [26:0] cnt = 27'd0;
    always @(posedge sys_clk) cnt <= cnt + 27'd1;
    assign led = cnt[26:23];
    (* keep *) PS7 ps7_i();
endmodule
\end{code}

\begin{mustknow}
Zynq 设计\textbf{必须实例化 PS7 模块}，即便完全不使用它。这样 nextpnr 会把
PS7 所有未使用的输入接地。若没有它，一旦内核使能 PL 到 PS 的电平转换器，
逻辑阵列就会驱动直连两个 Cortex-A9 核心的 nFIQ/nIRQ 线
（\cmd{IRQF2P[19:16]}，绕过中断控制器）。两个核心永远在 FIQ 处理中空转，
什么都不会打印出来。
\end{mustknow}

引脚约束来自 \rfile{bitstream/blinky/blinky.xdc}，一个普通的 XDC 文件，
nextpnr 直接读取。

\subsection{流程}

\rfile{bitstream/blinky/Makefile} 串联四个工具和一次格式转换：

\begin{code}
blinky.v  --yosys synth_xilinx-->  blinky.json
          --nextpnr-xilinx---->  blinky.fasm
          --fasm2frames------->  blinky.frames
          --xc7frames2bit----->  blinky.bit
          --bit2bin.py-------->  blinky.bin
\end{code}

\begin{shell}
cd bitstream/blinky && make blinky.bin
\end{shell}

最后一步 \rfile{bitstream/bit2bin.py} 之所以存在，是因为内核的 \cmd{zynq-fpga}
驱动期望 \cmd{bootgen} 生成的布局：去掉 \cmd{.bit} 的 ASCII 头，
每个 32 位字做字节交换。

\begin{checkpoint}
\cmd{xxd -l 16 blinky.bin} 显示 \cmd{ffff ffff ffff ffff 6655 99aa}，
即字节交换后的同步字。
\end{checkpoint}

\subsection{通过 SSH 加载}

FPGA manager 接受的是相对于 \file{/lib/firmware} 的文件\emph{名}：

\begin{shell}
ssh root@<ip> 'mkdir -p /lib/firmware; cat > /lib/firmware/blinky.bin' < blinky.bin
ssh root@<ip> 'echo blinky.bin > /sys/class/fpga_manager/fpga0/firmware;
               cat /sys/class/fpga_manager/fpga0/state'
\end{shell}

\rfile{tools/stage4-first-load/load-bitstream.sh} 做同样的事，但把内核日志通过
netconsole 重定向到工作站，第一次加载时值得这么做。

\begin{checkpoint}
\cmd{state} 读出 \cmd{operating}，四个 LED 闪烁，开发板的 22 端口仍然有响应。
\end{checkpoint}

\section{阶段 5：把比特流 API 做成镜像}

\subsection{服务}

\rfile{api/app.py} 是一个 FastAPI 应用，有三个端点：

\begin{center}\small
\begin{tabularx}{\textwidth}{@{}llX@{}}
\toprule
\cmd{GET} & \file{/state} & FPGA manager 状态以及最后加载的内容 \\
\cmd{POST} & \file{/bitstream} & multipart \cmd{file=}，\cmd{.bit} 或 \cmd{.bin}，可选 \cmd{?sha256=}；校验哈希，查找同步字，将 IDCODE 数据包与 XC7Z020 比对，转换 \cmd{.bit}，加载，待逻辑阵列就绪后返回 \\
\cmd{DELETE} & \file{/bitstream} & 加载 \file{empty.bin}（一个只含 PS7 的设计），因为 FPGA manager 没有卸载操作 \\
\bottomrule
\end{tabularx}
\end{center}

IDCODE 检查在头部查找 type-1 数据包 \cmd{0x30018001}，把紧随其后的字掩码到 28 位
后与 \cmd{0x23727093} 比较；最高四位是硅片版本号。错误以
\cmd{\{"error": "..."\}} 的形式返回，状态码 400 或 500。交互式文档在
\file{/docs} 提供。

\subsection{配方 (recipe)}

全部位于 \rfile{yocto/meta-ax7020}，路径相对于该层：

\begin{filelist}
  \item[\lfile{classes/pypi-wheel.bbclass}] 把纯 Python 的 wheel 解压到 site-packages 完成安装。scarthgap 没有 FastAPI 构建元数据所要求的 \cmd{pdm-backend} 对应的 class，而 wheel 本身就已经是安装后的目录树。
  \item[\file{recipes-devtools/python/}] fastapi 0.111.1、starlette 0.37.2、uvicorn 0.30.6、click 8.1.7、python-multipart 0.0.9 以 wheel 形式安装；pydantic、anyio 和 h11 来自 meta-python。
  \item[\lfile{recipes-devtools/uv/uv_0.12.13.bb}] astral 的 armv7-musl 静态二进制，哈希已固定，用于在板上做 \cmd{uv run --with ...} 实验。不在服务的启动路径上。
  \item[\lfile{recipes-support/ax7020-api/ax7020-api.bb}] 把 \file{app.py} 装到 \file{/opt/ax7020-api}，\file{empty.bin} 装到 \file{/lib/firmware}，并启用下面的 unit。
  \item[\lfile{recipes-core/images/ax7020-api-image.bb}] core-image-minimal 加上以上内容、Python、dropbear 和操作员公钥。\cmd{INITRAMFS\_MAXSIZE} 提高到 512\,MB。\textbf{不含}更新器。
\end{filelist}

\end{code}

\begin{mustknow}
API 镜像绝不能包含更新器。一旦设置了 \cmd{IMAGE\_URL}，它会在每次启动时
下载自己并 \cmd{kexec} 进入自己，无穷无尽。
\end{mustknow}

\subsection{构建、发布并更新维护系统}

\begin{shell}
source yocto/setup-build.sh
bitbake ax7020-api-image virtual/kernel        # API image + new maintenance FIT
tools/publish-image.sh AI-heimdall:/srv/ax7020-images
\end{shell}

带 systemd 更新器的维护 FIT 需要再烧进闪存一次。从运行中的 Linux 通过 SSH
完成，不用动跳线：\rfile{tools/flash-fit.sh} 上传文件，通过
\file{/dev/mtdblock3} 写入，回读并比对三个 MD5。如果 U-Boot 也重新编译过，
同一个脚本可以把 \file{u-boot.img} 写到 \file{/dev/mtdblock1}：

\begin{shell}
tools/flash-fit.sh <ip> tftp/fitImage          # mtd3, the FIT
tools/flash-fit.sh <ip> tftp/u-boot.img 1      # mtd1, U-Boot proper
\end{shell}

\begin{checkpoint}
脚本打印的三行 MD5 全部一致：本地文件、上传结果和闪存回读。
\end{checkpoint}

\subsection{冷启动}

断电。\textbf{拔掉 JTAG 适配器。}上电。

\begin{mustknow}
留在 JTAG 口上的 FT232H 会把 TMS 保持在 3.3\,V，并通过保护二极管让开发板的 3.3\,V
电源轨和闪存芯片在断电期间保持带电。一颗被 Linux 会话留在 4 字节地址模式的闪存
芯片就此永远不会复位，而使用 3 字节地址读取的 boot ROM 会停在 \cmd{0xffffff28}。
只有拔掉适配器，"重新上电"才算数。
\end{mustknow}

\begin{checkpoint}
大约一分钟内，无人登录的情况下，DHCP 服务器为 \cmd{ax7020} 保留的地址上
8000 端口有响应，可以送入一个比特流：
\begin{shell}
IP=$(curl -s http://10.42.0.1:8000/get_all_network_clients \
     | jq -r '.clients[] | select(.hostname=="ax7020" and .active_lease) | .ip')
curl http://$IP:8000/state
curl -F file=@bitstream/blinky/blinky.bit http://$IP:8000/bitstream
\end{shell}
\begin{code}
{"state":"operating", "sha256":"f69a32d2...", "bytes":4045524,
 "idcode":"0x03727093", "filename":"blinky.bit"}
\end{code}
\end{checkpoint}

\section{日常操作}

\subsection{找到开发板}

U-Boot、维护内核和 API 内核各自申请自己的 DHCP 租约，所以一次启动过程中地址会变。
按主机名查询 DHCP 服务器，而不是记住某个地址。上文使用的资产查询 API 是
\href{https://github.com/MaxClerkwell/dhcp-inventory-api}{dhcp-inventory-api}；
任何 DHCP 服务器的租约文件都可以用同样的方式处理。

\subsection{SSH}

根文件系统在 RAM 中，所以 dropbear 每次启动都会生成新的主机密钥。每次会话前：

\begin{shell}
ssh-keygen -R <ip>
\end{shell}

启动后紧接着出现的 \cmd{Connection refused} 只说明 dropbear 还没起来；
在这颗 CPU 上生成密钥大约需要 30\,s。

\subsection{回滚镜像}

在镜像服务器上把 \file{ax7020-latest} 指向一个旧目录，然后给开发板重新上电。
闪存中的内容不会有任何变化。

\subsection{重写闪存}

从运行中的 Linux 用 \rfile{tools/flash-fit.sh} 重写 FIT（mtd3）和完整 U-Boot（mtd1）。
\file{boot.bin}（mtd0）只通过阶段 1 的 JTAG 流程写入，环境变量分区（mtd2）归 U-Boot 管。

\subsection{备份闪存}

从 U-Boot 通过 TFTP：

\begin{shell}
tools/ncsh.py <ip> "sf probe 0 30000000 0" "sf read 0x10000000 0 0x2000000" \
  "md5sum 0x10000000 0x2000000" "tftpput 0x10000000 0x2000000 ax7020-qspi.bin"
\end{shell}

\section{下一步}

作为实验室系统，这条流水线已经完整。再加三项，它就能面向更大的网络，按此顺序：

\begin{enumerate}
  \item API 的\textbf{身份认证}。带 AXI master 的比特流拥有对系统内存的完全访问权；
        加载未经审查的比特流，等同于多绕了几步的远程代码执行。
  \item \textbf{清单中加入比特流。}第四行 \cmd{bitstream <file> <sha256>}，
        由服务在启动时加载，这样启动后逻辑阵列就不会是空的。
  \item \file{/etc/ax7020-release} 中的\textbf{构建标记}，由 \file{/state} 报告，
        这样就能区分正在运行的镜像、闪存中的镜像和服务器上的镜像。
\end{enumerate}
